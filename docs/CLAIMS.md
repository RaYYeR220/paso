# Claims

Every public claim Paso makes, with its evidence. Checked on 2026-10-12 and 2026-10-13 against Stellar mainnet and testnet, Base and Base Sepolia, Arc Testnet, and, for the routes in claims 67 to 71, all ten EVM networks listed there.

| Tag | Meaning |
|---|---|
| `REPRODUCIBLE` | A command anyone can run. The expected result is stated. |
| `VERIFIED LIVE` | A transaction on a public network, linked. |
| `BUILT, NOT RUN LIVE` | Code and tests exist. No live transaction is recorded. |
| `NOT CLAIMED` | Not done, or not asserted. |

The project has reviewed its own contracts adversarially and published what it found in [AUDIT.md](AUDIT.md). Claims 1, 6, 9, 10, 14 and 36 carry the limits that review found. It is not a third-party audit; see claims 50 to 53. Claims 58 to 61 say what the SDK and the app now do about those findings. Claims 67 to 77 cover the five EVM chains and the npm package.

Commands assume a clone with `pnpm install` done. `pnpm verify` and `stellar tx fetch` read a public Soroban RPC, which keeps about a week of transactions; explorer links outlive that. Step numbers refer to [VERIFY.md](VERIFY.md).

## Not claimed

- **Audited.** There is no third-party audit and no formal verification, on either network. The project's own review ([AUDIT.md](AUDIT.md)) is neither.
- **Safe payment to any address.** USDC sent to the account of an address with no private key cannot be recovered, and such an address cannot always be recognised in advance.
- **Revocable signatures.** A signature stays usable until its expiry, even if its transaction failed. The account has no revoke function and no key rotation.
- **A large or long-running mainnet service.** The hosted app and its relayer have served one mainnet run, with a scripted wallet. On mainnet the app brings over at most 25 USDC at a time and the relayer spends at most 2 XLM of fees a day.
- **Transfers on every listed chain.** Base has run on both networks and Arc on testnet. No transfer has been made from or to Ethereum, Arbitrum or OP Mainnet on either network, or from or to Arc on mainnet (claim 75). CCTP chains other than these five are not supported: the SDK does not list them and the relayer refuses their domains.
- **Key recovery or rotation.** A lost Ethereum key is a lost account.
- **Smart-contract wallets.** ERC-1271 signatures are not accepted. Neither are passkeys or multisig. USDC sent to the account of a smart-contract wallet is lost.
- **"First".** Paso does not claim to be the first at any part of this. See prior art below.
- **A readable message for every call.** Nested arguments appear as hashes, and so does a muxed (`M…`) recipient of a transfer. Amounts are raw integers and contracts are addresses. The signature's expiry is not displayed. The network is not named in words: it is a 32-byte salt.
- **Tested wallets.** No wallet extension and no hardware wallet has been tested. The wallet path has been exercised by a scripted wallet only.
- **A verified build on stellar.expert.** CI rebuilds the deployed code on every push and compares hashes (claim 62), and `pnpm verify` compares the code hash on chain with the one recorded here. No build attestation exists for the deployed code.
- **A decentralised or always-on relayer.** It is one server with in-memory limits. It can decline. The fallback is to submit from any funded account.
- **Long-lived accounts.** Every account here is hours old. The contracts never extend TTLs. The shared account code and the hub are archived after ledger 66,981,816, about 9 February 2027, unless someone pays to extend them; anyone can. Restoring an archived account has not been exercised.
- **An exit that cannot be blocked.** Every `hub.exit` reaches Circle with the hub as caller. If Circle blocks the hub, `exit` stops for every account; funds stay in the accounts, and an account can still call Circle's contract itself.
- **Typical mainnet fees.** The mainnet figures are one or two samples each, from two runs.
- **Load.** No load test has been run.
- **Privacy.** Owner addresses, account addresses and calls are public.

## Statements about other projects

These come from those projects' public material and are not verified by anything in this repository.

- MetaMask's Stellar support creates a classic account that needs 1 XLM plus 0.5 XLM per trustline, in MetaMask only.
- EIP-712 verification inside a Soroban `__check_auth` exists in LayerZero's OneSig multisig for Stellar.
- OpenZeppelin's Stellar smart accounts ship ed25519 and WebAuthn verifiers.

Paso's part is narrower: an account derived from the Ethereum address itself, with the displayed message rebuilt on chain from the calls being authorised.
